🎯 技術的な課題と、その解決

CASE 01
クライアントを信用しないゲームプレイ設計
課題
複数プレイヤーが同じ畑を共有するため、所持金やアイテムをクライアント側で書き換えられると成立しない。作物の成長も、途中参加したプレイヤーと既存プレイヤーで表示がずれてはいけない。
アプローチ
状態を変える処理はすべて [Command] でサーバーへ送り、SyncVar / SyncList の更新はサーバー側だけが行う構成に統一。成長はローカル時間ではなく NetworkTime.time を基準にした期限で管理し、遅れて参加したクライアントでも同じ段階が再現されるようにしました。
結果
クライアントは入力送信と描画のみを担当する構成に。購入時にインベントリが満杯だった場合に代金を返金する処理まで含め、状態が食い違わないようにしています。

コード： PlayerShopServer.cs ／ Plant.cs

CASE 02
計測を起点にした描画最適化（Draw Call −69%）
課題
畑・柵・建物が増えるにつれてフレームレートが低下。オブジェクトごとに個別のテクスチャとマテリアルを持っていたため、描画命令数とテクスチャメモリの両方が膨らんでいた。
アプローチ
Frame Debugger でバッチが分断されている箇所を特定した上で、①複数のテクスチャを1枚のアトラスへ統合してマテリアル数を削減、②自作の MeshCombiner で静的オブジェクトのメッシュを結合、③同一マテリアルになったオブジェクトに GPU インスタンシングを適用、の順で対処しました。
結果
Draw Call 286 → 88（−69%）、平均 FPS 111 → 135（フレームタイム換算で約 9.0ms → 7.4ms）。
計測条件と内訳
計測環境（CPU / GPU / RAM）要記入
ビルド構成要記入（Editor / Standalone・Development ビルドの別）
解像度・品質設定要記入
計測シーン・サンプル同一シーン・同一設定・同一視点／要記入 フレームの平均

SetPass Calls / Batches要記入

CASE 03
ネットワークコードからドメインロジックを切り離す
課題
インベントリのスタック処理は境界条件（容量オーバー、スタック不可アイテム、部分的な取り出し）でバグが出やすい。しかし SyncList を直接触るコードは Unity を起動しないと動かせず、検証手段が手動プレイしかなかった。
アプローチ
ロジックを InventoryModel という純粋な C# クラスへ抽出し、SyncList ではなく IList<InventorySlot> を受け取り、スタック上限は IItemStackRules 越しに取得する形に変更。専用の asmdef で Unity 非依存アセンブリに分離し、テストでは FakeRules を注入しています。
結果
Unity を起動せず NUnit でロジックを検証できる構成に。現在テストしている範囲はインベントリのみ（7ケース）で、「容量不足の追加は在庫を一切変更しない」といった不変条件を保証しています。

コード： InventoryModel.cs ／ InventoryTest.cs

🧩 主な機能と設計判断

領域やったことなぜそうしたか
農業システム設置のゴーストプレビュー、成長段階の進行、収穫までをサーバー基準で同期設置可否をクライアントで判断させないため
インベントリ9スロットを SyncList で同期し、ロジックは別アセンブリへ分離同期は Mirror に任せ、ルールはテスト可能に保つため
ショップ / 経済売買をサーバーで検証、作物サイズに応じて売値が変動。UIは Zenject の Factory で動的生成価格計算をクライアントに渡さないため
インタラクションレイキャスト + IInteractable でドア・作物・ショップを統一操作対象を増やすときに既存コードを変更しないため
アイテム定義ItemConfig を基底とする ScriptableObject 継承ツリー＋エディタ拡張でDB自動生成コンテンツ追加でコードを触らずに済ませるため
🔍 現時点でできていないこと
  • ネットワークの範囲：Host/Client 構成までで、専用サーバー・再接続処理・レイテンシ／パケットロス下での検証・本格的なチート対策は未対応です。まず Mirror の LatencySimulation で遅延環境の挙動を確認するところから進めます。
  • データ永続化：セーブ／ロードが未実装のため、切断すると進行が失われます。再接続時に状態を復元する仕組みが次の実装課題です。
  • テスト範囲：インベントリのみ。売買処理を NetworkBehaviour から ShopService として切り出し、対象を広げる予定です。
  • アイテムDBの取得経路：ItemDatabase.Instance によるシングルトンアクセスが残っています。NetworkServer.Spawn で生成されるオブジェクトが Zenject のコンテキスト外になるためで、ZenjectBinding とカスタムファクトリでの解消を検討しています。

🎯 チーム開発における課題と、その解決

CASE 01
全員が同時に動けるように、作業境界を設計する
課題
チーム内で Unity エディタの経験があるのは自分だけ。全員が同じシーンを編集すると衝突が頻発し、短期のジャムでは統合が間に合わなくなる。
アプローチ
「自分が全部やる」ではなく、メンバーが得意なロジック実装に集中できる形に環境を整えることを役割にしました。具体的には、プロジェクト設定・シーン構成・.gitignore とブランチ運用を自分が用意し、メンバーにはシーンではなくスクリプト単位で実装してもらう分担に。上がってきたコードのレビューと Unity 側への組み込みを自分が担当しました。
結果
4名が並行して作業してもシーン競合を起こさずに完成。プルリクエストでレビューしてから統合する流れがチームに定着しました。
CASE 02

🎯 取り組んだこと

CASE 01
描画パイプラインとスキニングを自前で組む
課題
エンジンがない状態では、頂点データを画面に出すまでに必要なリソース管理・状態設定をすべて自分で用意する必要がある。ボーンアニメーションも既製のシステムなしで動かさなければならない。
アプローチ
デバイス／スワップチェーンの初期化から、頂点・インデックス・定数バッファの生成と更新、入力レイアウト、深度ステンシル、シェーダーのコンパイルとバインドまでを実装。アニメーションは Assimp でボーン階層とウェイトを読み込み、ボーン行列を定数バッファへ送って頂点シェーダー側でスキニングを計算する方式にしました。
結果
Unity の Material / SetPass / SkinnedMeshRenderer が内部で何をしているかを具体的に説明できるようになり、描画最適化を判断する根拠になっています。
